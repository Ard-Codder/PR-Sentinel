# Отчёт о реализации PR Sentinel

Дата: 25 ноября 2026. Репозиторий локальный, коммит и push не делались.

## Что получилось

Рабочий локальный агент в одном процессе. Команды `uv run pr-sentinel once` и `uv run pr-sentinel loop` ищут открытые PR, где текущий пользователь есть в `requested_reviewers`, пропускают уже разобранный SHA, фильтруют diff, спрашивают LM Studio и либо пишут результат в лог, либо обновляют один комментарий в GitHub.

`DRY_RUN=true` по умолчанию и в коде, и в `.env.example`. Без явного `DRY_RUN=false` методы записи в GitHub не вызываются.

Проверка без токена на этапе реализации: `uv run pr-sentinel once` завершился с кодом 1 и сообщением `GITHUB_TOKEN is not set`. Позже в `.env` добавлен токен; этот запуск описан ниже и не заменяет ту проверку.

## Архитектура

Модульный монолит, без очереди, веб-интерфейса и отдельных процессов.

- `ReviewService` опрашивает PR и ведёт один PR от блокировки SHA до статуса.
- `GitHubClient` ходит в REST API. Для fine-grained PAT нужна только роль **Pull requests: Read and write**. Metadata: Read GitHub ставит сам. Contents и Issues не запрашиваются: патч берётся из `GET /pulls/{n}/files`, комментарий PR пишется через issue comment, который эта роль уже разрешает. Search API не используется.
- `DiffProcessor` выкидывает файлы без патча, бинарные, lock-файлы, `vendor/`, `dist/`, `node_modules/`, минифицированные файлы и слишком большие патчи. Оставшиеся файлы режутся по бюджету символов, не больше 4 последовательных запросов.
- `ReviewEngine` собирает промпт и читает только `message.content`. Если JSON или схема не сошлись, один повтор. Второй провал — это ошибка, не успешное ревью.
- `ResultValidator` снимает дубликаты по файлу, строке и нормализованному тексту. Строка принимается только если в diff она добавлена или изменена (префикс `+`). Чужой файл, контекст и удаления отбрасываются.
- `ReviewPublisher` собирает markdown с маркером `<!-- pr-sentinel -->`.
- `StateStore` на SQLite. Таблица `reviews` хранит статус конкретного `repo + PR + SHA`. Таблица `pr_comments` хранит один `comment_id` на PR. Новый SHA обновляет тот же комментарий. Новый комментарий создаётся, только если своего ещё нет или GitHub ответил 404 на обновление.

Статусы:

- `published` — комментарий записан, тот же SHA больше не анализируется.
- `dry_run` — анализ в безопасном режиме закончен. Пока `DRY_RUN=true`, модель для этого SHA не вызывается снова. Запуск с `DRY_RUN=false` этот статус за публикацию не считает.
- `skipped` — после фильтра не осталось файлов с добавленными или изменёнными строками. Тот же SHA не повторяется.
- `error` — сбой GitHub после ретраев, сбой LLM, неразобранный ответ или замечания, из которых валидатор не оставил ни одного. Следующий опрос повторяет SHA.
- `stale` — SHA сменился до публикации. Комментарий не пишется.
- `in_progress` старше 30 минут считается зависшим и повторяется.

Сеть: до 3 попыток на 429, 500, 502, 503, 504 и обрыв соединения, с учётом `Retry-After`. 401 и 403 не крутятся в цикле запроса. Токен попадает только в `Authorization` и вырезается из логов.

## Финальная проверка на GitHub, 25 ноября 2026

`DRY_RUN` не менялся и после прогонов остался `true`. Комментарии не публиковались, pull request не создавался.

Реальный клиент приложения с токеном из `.env`:

- `GET /user` вернул 200, логин `Ard-Codder`.
- Репозиторий `Ard-Codder/PR-Sentinel` доступен, `private=false`, ветка по умолчанию `main`.
- `GET /repos/Ard-Codder/PR-Sentinel/pulls` для `state=open`, `closed` и `all` вернул пустые списки. Открытого PR, где пользователь назначен ревьюером, нет.

Два запуска `uv run pr-sentinel once` завершились с кодом 0. В логе каждого только чтение:

- `GET https://api.github.com/user` — 200
- `GET https://api.github.com/repos/Ard-Codder/PR-Sentinel/pulls?state=open&per_page=100&page=1` — 200
- `Found 0 pull request(s) assigned for review`

Запросов `POST` и `PATCH` в логе нет. LM Studio в этих двух запусках не вызывалась: до diff выполнение не дошло. Файл `data/state.db` создался при открытии хранилища, таблицы `reviews` и `pr_comments` пустые. Записи о проверке SHA нет, поэтому повторный запуск нельзя считать проверкой идемпотентности на реальном PR.

Не выполнялось на реальном PR: получение diff, генерация замечаний, валидация замечаний, запись статуса `dry_run` в SQLite, пропуск того же SHA при втором запуске.

## Тесты на моках, выполненные при реализации

Команда обычного прогона:

```bash
uv run pytest -q
```

Результат:

```text
22 passed, 1 deselected in 0.21s
```

Живой вызов LM Studio, в обычный прогон не входит:

```bash
uv run pytest tests/test_live_llm.py -o addopts= -m integration -q
```

Результат:

```text
1 passed in 0.69s
```

Моки GitHub и LLM покрывают такой сценарий:

- фильтр diff и нарезка на части, не больше 4;
- валидатор оставляет изменённую строку и отбрасывает контекст, чужой файл и дубликат;
- пустой список замечаний публикуется как успешное ревью;
- неразобранный JSON после одной повторной попытки не публикуется и остаётся `error`, следующий проход повторяет проверку;
- если все замечания отвергнуты, комментария нет и SHA можно повторить;
- `comment_id` живёт на PR, а не на SHA; новый коммит обновляет тот же комментарий;
- `skipped` не повторяется, `error` повторяется;
- dry-run не вызывает создание и обновление комментария;
- смена SHA перед публикацией комментарий не пишет;
- клиент GitHub повторяет 429 и не повторяет 401;
- список PR оставляет только тех, где пользователь назначен ревьюером;
- удалённый комментарий (404) создаётся заново, существующий с маркером переиспользуется, даже если локальной записи ещё нет.

Живой тест попросил модель вернуть `{"summary":"ok","findings":[]}` на `http://127.0.0.1:1234/v1` и разобрал ответ.

## Ограничения

- Полный цикл ревью на реальном PR не запускался: в `Ard-Codder/PR-Sentinel` нет ни одного pull request. Чтобы его пройти, нужен открытый PR, где `Ard-Codder` указан в requested reviewers. После этого снова `uv run pr-sentinel once` при `DRY_RUN=true`.
- Публикация комментария в GitHub не проверялась живьём и в этой сессии намеренно не включалась.
- Комментарий один на PR. Inline-заметок и статусов approve/request changes нет.
- Замечание можно привязать только к строке с префиксом `+`. PR из одних удалений помечается `skipped`.
- Файл, который не влез в 4 части, перечисляется в комментарии как непросмотренный. Отдельной очереди для него нет.
- За проход не больше 5 PR, ревью по очереди.
- Если список репозиториев пуст, берутся репозитории токена, не больше 20, без Search API.
- Адрес `192.168.3.5:1234` в этой сети не используется.
